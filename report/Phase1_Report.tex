\section{Introduction and objective}

Phase 1 implements a lexical-analyzer generator for the supplied regular
specification of a small Java subset. The generator constructs token
automata, combines and determinizes them, minimizes the DFA, prints the
minimized transition table, and emits an independent C++ lexical analyzer
that simulates that DFA. The generated analyzer recognizes tokens,
records identifier lexemes in a symbol table, and reports lexical errors
while continuing to scan.

The scope of this report is Phase 1 only. Parser integration and the
optional Lex/Flex bonus task are not included.

\section{System overview}

The implemented data flow is:

\begin{center}
\code{Lexical rules}
$\rightarrow$ \code{RuleParser}
$\rightarrow$ \code{RegexPreprocessor}
$\rightarrow$ \code{RegexParser}
$\rightarrow$ \code{ThompsonConstructor}
$\rightarrow$ \code{NFA::combine}
$\rightarrow$ \code{DFA::fromNFA}
$\rightarrow$ \code{DFA::minimize}
$\rightarrow$ \code{transition table}
$\rightarrow$ \code{generated lexer}
\end{center}

The driver in \code{src/lexer/main.cpp} parses the rules, builds the
combined NFA, constructs and minimizes the DFA, prints the minimized
table, and writes \code{generated\_lexer.cpp}. The generated program
contains the minimized DFA data and performs scanning without linking to
the generator or rebuilding automata at runtime.

\section{Data structures}

\begin{description}
    \item[Parsed rules.] \code{ParsedRules} stores regular definitions in
    an unordered map, regular expressions in an ordered vector, and
    keywords and punctuation in vectors. Keeping regular expressions in
    input order supports the specified first-listed-rule priority.
    \item[Regular-expression syntax tree.] \code{RegexNode} is a
    \code{unique\_ptr}-owned tree. Its node types represent symbols,
    epsilon, concatenation, alternation, Kleene star, and positive
    closure.
    \item[Finite automata.] The common \code{FA} base stores a start-state
    ID and an accepting-state map. Each \code{AcceptState} records its
    state ID, priority, and token class.
    \item[NFA transitions.] \code{NFATransitionTable} maps a state and
    input symbol to a set of destination states. The null character
    \code{'\textbackslash 0'} denotes epsilon and is excluded from the
    input alphabet.
    \item[DFA transitions.] \code{DFATransitionTable} maps a state and
    input symbol to one destination state. A missing transition is
    returned as \code{-1}.
    \item[Token and symbol table.] \code{Token} contains a token class
    and an attribute string. \code{SymbolTable} stores identifier
    lexemes in an unordered set, avoiding duplicate entries.
    \item[Generated tables.] The standalone program embeds state IDs,
    a nested map of DFA transitions, the start state, and an accepting
    map containing token class and priority.
\end{description}

\section{Algorithms and techniques}

\subsection{Rule parsing and regular-expression preprocessing}

\code{RuleParser} recognizes \code{LHS = RHS} definitions,
\code{LHS: RHS} expressions, keyword lists in braces, and punctuation
lists in brackets. For expression rules it preserves separators long
enough for the preprocessor to distinguish a definition name following a
literal. The preprocessor expands character ranges and recursively
expands named definitions while preserving escaped symbols and guarding
against circular definitions.

\code{RegexParser} builds the syntax tree using alternation, implicit
concatenation, postfix repetition, and atoms. The supplied specification
uses \code{|}, \code{+}, \code{*}, parentheses, ranges, and backslash
escapes; \code{\textbackslash L} is parsed as epsilon.

\subsection{Thompson construction and NFA combination}

Thompson construction creates a two-state fragment for a symbol or
epsilon. Concatenation joins fragments by an epsilon transition;
alternation introduces a split and join; star adds skip, repeat, and exit
epsilon transitions; positive closure requires an initial traversal and
then permits repetition or exit. Each token NFA has an accepting state
carrying its token class and priority.

The factory builds literal NFAs for reserved keywords and punctuation
and expression NFAs for named token rules. \code{NFA::combine} assigns
disjoint state IDs and connects a new common start state to each
individual start using epsilon transitions.

\subsection{Subset construction}

\code{DFA::fromNFA} represents each DFA state as a set of NFA states.
It computes the transitive epsilon closure of the initial state set and
after each move. For each input symbol it unions destinations, closes
the result, and reuses an existing DFA state when the same subset has
already been seen. If a subset contains multiple accepting NFA states,
the smallest priority wins; missing transitions remain absent.

\subsection{DFA minimization}

\code{DFA::minimize} considers states reachable from the start state.
Its initial partition signature distinguishes non-accepting states from
accepting states and also distinguishes accepting states by both token
class and priority. It repeatedly refines partitions according to their
destination partitions for every reachable alphabet symbol. The
minimized DFA is then traversed from its start partition to assign
compact state IDs. Missing transitions are modeled through a rejecting
sink during refinement and omitted from the emitted partial DFA.

\subsection{Scanning, priority, and recovery}

The generated scanner skips whitespace, starts at the DFA start state,
and advances one input character at a time. It records the most recent
accepting state and position while following transitions; when a
transition is missing or input ends, it emits the longest accepted
prefix and resumes at that position. The DFA's acceptance metadata
preserves rule priority, and the scanner also compares priority when
accepting candidates have the same length.

The factory processes keywords as reserved literal tokens, before
punctuation and regular expressions. Within the regular-expression
list, order is retained, so the first listed expression wins equal-length
ties. Each emitted token uses its lexeme as its attribute. Lexemes whose
class is \code{id} are inserted into the symbol table. If no token is
accepted at the current position, the scanner reports the offending
character and advances by one character, allowing later input to be
scanned.

\section{Supplied lexical rules}

The following listing reproduces \code{examples/lexical\_rules.txt}
without rewriting its expressions:

\begin{lstlisting}
letter = a-z | A-Z
digit = 0 - 9
id: letter (letter|digit)*
digits = digit+
{boolean int float}
num: digit+ ( \L | E digits | . digits ( \L | E digits))
relop: \=\= | !\= | > | >\= | < | <\=
assign: =
{ if else while }
[; , \( \) { }]
addop: \+ | \-
mulop: \* | /
\end{lstlisting}

The identifier rule requires a letter followed by zero or more letters
or digits. The number rule follows the assignment's prose definition and
accepts integer and decimal forms, each with an optional exponent. The
keyword sets together contain \code{int}, \code{float}, \code{boolean},
\code{if}, \code{else}, and \code{while}. The relational operators are
specified by \code{relop}, assignment by \code{assign}, addition and
subtraction by \code{addop}, and multiplication and division by
\code{mulop}. The punctuation list contains semicolon, comma,
parentheses, and curly brackets.

\section{Generated lexical analyzer}

The standalone C++ source embeds the start state, all minimized states,
the transition map, and accepting-state class/priority information. It
uses those tables directly and does not use regular expressions or
reconstruct the NFA or DFA. The generated source depends only on the C++
standard library.

The generated program accepts source from a file argument or standard
input. The lexer class provides a \code{nextToken} method that reads
characters from the stream as needed and returns one token at a time. A lookahead buffer
retains characters needed to finish maximal-munch matching without
loading the entire source file. The standalone \code{main} repeatedly
calls this method and prints each token class with its lexeme as the
attribute. Identifier lexemes are inserted into the symbol table. On an
unrecognized character the lexer writes an error to standard error,
advances one character, and continues. It uses \code{std::isspace} to
skip whitespace.

\section{Assumptions and justifications}

\begin{enumerate}
    \item \textbf{Number-rule ambiguity.} The prose permits an optional
    exponent after an integer or decimal number, while the supplied
    example expression places it only after the decimal alternative.
    This implementation follows the prose. Its rule is
    \[
        \code{num: digit+ ( \textbackslash L | E digits | . digits ( \textbackslash L | E digits))}
    \]
    so \code{123E4} and \code{12.34E5} are each one number token. If
    the instructor requires the exact example rule, replace it with
    \code{num: digit+ | digit+ . digits ( \textbackslash L | E digits)};
    the lexer and DFA must then be regenerated from the rules file.
    \item \textbf{Attribute representation.} The assignment requires
    an attribute value but does not define a separate encoding. The
    implementation uses the matched lexeme as the attribute, preserving
    the source spelling for each token.
    \item \textbf{Reserved words.} The specification says keywords are
    reserved. They are built as literal tokens before the general
    regular-expression rules. Maximal munch still makes a longer word
    such as \code{ifx} an identifier.
    \item \textbf{Parser phase boundary.} The generated lexer exposes
    \code{Lexer::nextToken()} so a future parser can request tokens
    individually. The parser itself belongs to Phase 2 and is not
    implemented here.
    \item \textbf{Example capitalization.} The PDF's illustrative token
    stream writes \code{Id} once, while the lexical rule and actual
    implementation use the token class \code{id}. The report records
    the implementation's lowercase output.
    \item \textbf{Punctuation glyph.} The PDF text layer represents
    the semicolon in its punctuation example with U+037E, while the
    lexical-rules file and supplied program use ASCII semicolon
    U+003B. The implementation uses ASCII semicolon, consistent with
    the prose requirement and test program.
\end{enumerate}
